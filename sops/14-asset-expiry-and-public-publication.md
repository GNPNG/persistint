# SOP-14: Asset expiry at stage gates, and publication to a public mirror

Status: draft, 2026-10-24. Origin: a private reference sheet moved out of the public tree by rename,
so the public mirror kept serving it; the fix required a history rewrite that also rewrote the
private repository because the public mirror was a plain push mirror.

## The rule, with its reasoning

1. **Working assets expire.** An asset that was needed during early development (reference sheets,
   placeholders, scratch renders) is legitimately in the repository while it is used. When the thing it
   supported ships, it has expired. Expiry is a state of the asset, not a judgment of its quality.
2. **Expiry is annotated at creation.** Every asset of that kind carries, in the asset manifest, the
   stage at which it expires (`expires: 0.1.0`, `expires: first-playtest`, `expires: when <generator>
   output lands`). An expiry nobody wrote down is an expiry nobody will notice.
3. **Stage gates sweep expired assets.** The gate from one minor stage to the next (`0.0.x` to `0.1.x`,
   and every minor after it) runs the expiry sweep: list assets whose expiry stage has passed, plus
   assets referenced by nothing, and remove them from the public tree in the release commit. The sweep
   is a script and its output is attached to the release ticket.
4. **The private repository keeps everything.** History is never rewritten in the private repository:
   the point of the private history is to replay the project later. Expired assets are removed from the
   tree, not from history.
5. **The public repository gets a publication, not a mirror.** A plain push mirror couples the two
   histories: anything that ever entered the private repository reaches the public one, and the only way
   to remove it publicly is to rewrite privately. So publication to a public forge is a derived
   artefact: a filtered history (private folders, expired assets and any purged paths excluded),
   regenerated by a script at each release and force-pushed to the public repository, which is treated
   as disposable. Nobody develops against the public repository.
6. **If a mirror exists anyway, it is the hose, and it is on the author's finger.** A push mirror is
   acceptable only while nothing in the private repository would hurt in public; the day that stops being
   true, the mirror is replaced by the publication script, not patched.

## Gate record (HACCP form)

- Hazard: expired or private material reaching the public repository; a history rewrite forced on the
  private repository.
- Critical control point: the minor-version gate; the publication step of the release.
- Critical limits: expiry sweep returns empty or its removals are in the release commit; the public
  publication is generated from the filter list and contains no path on the private list.
- Monitoring: count of expired assets found per gate; count of private paths in the public publication
  (must be 0); whether the private history was rewritten (must be never).
- Corrective action: add the missed asset type to the manifest rules; add the path to the filter list;
  never rewrite the private history to fix a public leak.
- Verification: the reviewer tier checks the gate record at each release.
- Records: the sweep output and the publication log, attached to the release ticket.

## Edge cases (clauses proposed 2026-10-24, pending the author's approval; once approved, no instance is asked again)

E1. **A private history rewrite has already happened** (as on 2026-10-24, before this SOP existed).
    Restore the private repository's history from the most recent complete backup (bundle, backup
    branch or forge copy) and push nothing rewritten to it; the rewritten history becomes the public
    publication. If no complete backup exists, keep the rewritten private history and record the gap
    (what was removed, when, why, where a copy survives) on the release ticket.

E2. **A rewrite is unavoidable** (a credential or legally unpublishable material entered the
    private history). Before rewriting, archive the pre-rewrite history as a bundle in the private
    store with the date and the reason; rewrite; record the gap as in E1. The archive is private
    research data, never published.

E3. **The public repository already holds material that is now private or expired.** Regenerate the
    public publication from the filter list and force-push it; the private repository is untouched.
    Ask the forge host to purge unreachable objects if the material matters.

E4. **A mirror is still in place when E3 occurs.** Delete the mirror first, then publish; the mirror
    is not re-created, the publication script replaces it.

## Publication trigger (added 2026-10-25, the author's ask: the pace of work visible without a mirror)

The author's words: "I want people to see the pace of work we're doing; but if you wanted to be able to trigger a push mirror maybe with a version increment, and you can help me set that up on a gitea trigger, on a hook on your side, that would work for me too." And on the alternative: "like pushing a special release branch that we clean up or something."

**Why not a mirror interval, and why not a cleaned release branch.** A push mirror cannot filter: whatever is on the private forge, every branch, every blob, reaches the public repository within the interval, and the interval only sets how long there is to notice. Four hours is not safe for the same reason fifteen minutes is not: the control is in the wrong place. A cleaned release branch is the same idea done by hand: it still carries the private history's objects unless the history is rewritten, and rewriting by hand each release is the mistake SOP-14 exists to prevent. The filtered publication (`tools/publish_public.sh`) is the cleaned release branch done mechanically and completely: a fresh mirror of the private repository, `git filter-repo` over the path list and blob list, force-push of main and tags to the public repository. The private forge is never rewritten; the public repository is disposable and regenerated.

**Trigger.** Two events run the publication, both from a machine that is not the author's laptop and not an agent session (so the publication never depends on who is at a keyboard):

1. Every push to `main` on the private forge: the public repository then shows the same pace of work as the private one, filtered. Public commits carry the same messages and times; only the removed paths differ.
2. Every version tag `v*`: the tag is published with the same filter, so a release on the public repository is a release on the private one.

**Mechanism, in order of preference.**

- Gitea Actions on the private repository with a registered runner: `.gitea/workflows/publish-public.yml` runs `tools/publish_public.sh` on push to `main` and on tags, with the public repository's write token as the repository secret `PUBLIC_PUSH_TOKEN`. One-time provisioning: enable Actions on the instance, register a runner (srv is the intended host), add the secret.
- Without a runner: `tools/publish_public_cron.sh` on srv, every 15 minutes, fetches the private repository, compares `main` and the tags with the last published state, and runs the publication only when something changed. Same token, from a file readable only by the service user, never from the environment of an interactive session.

**Gate.** The publication runs only after the filter lists are current (the expiry sweep of this SOP) and only from the private `main`; no other branch is ever published. The push mirror is deleted when the first trigger run is confirmed on the public repository (the author's E4), and the mirror is never re-created.

**What the public repository is for.** The author's words: "The benefit we get from Github is also a better public wiki and public bug reports." So the public repository carries the public wiki and the public issue tracker; the private forge carries the working source, the team tracker and the history. Every publication carries `AGENTS.md` at the repository root, which states in plain words that the GitHub copy is a filtered publication of a private repository hosted at GNPNG/GNOMATIX, that its history is regenerated, that bugs go to GitHub issues and that an agent which checked it out as the working source should stop and ask for the private forge. The author's words for the need: agents "get confused and checkout the github repo thinking that's the working source." The file lives in the private repository so the publication carries it unchanged.

**Record.** Each run appends one line to the publication log in the private repository's wiki or the vault (date, private commit, public commit, filter list hash, runner); a run whose filter list hash differs from the previous run is flagged for a human look before the next.
