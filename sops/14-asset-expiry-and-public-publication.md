# SOP-14: Asset expiry at stage gates, and publication to a public mirror

Status: draft, 2026-10-24. Origin: a private reference sheet moved out of the public tree by rename,
so the public mirror kept serving it; the fix required a history rewrite that also rewrote the
private repository because the public mirror was a plain push mirror.

## The rule, with its reasoning

1. **Working assets expire.** An asset that was needed during early development (reference sheets,
   placeholders, scratch renders) is legitimately in the repository while it is used. When the thing it
   supported ships, it has expired. Expiry is a state of the asset, not a judgment of its quality.
2. **Expiry is annotated at creation.** Every asset of that kind carries, in the asset manifest, the
   stage at which it expires (`expires: 0.1.0`, `expires: first-playtest`, `expires: when <generator>
   output lands`). An expiry nobody wrote down is an expiry nobody will notice.
3. **Stage gates sweep expired assets.** The gate from one minor stage to the next (`0.0.x` to `0.1.x`,
   and every minor after it) runs the expiry sweep: list assets whose expiry stage has passed, plus
   assets referenced by nothing, and remove them from the public tree in the release commit. The sweep
   is a script and its output is attached to the release ticket.
4. **The private repository keeps everything.** History is never rewritten in the private repository:
   the point of the private history is to replay the project later. Expired assets are removed from the
   tree, not from history.
5. **The public repository gets a publication, not a mirror.** A plain push mirror couples the two
   histories: anything that ever entered the private repository reaches the public one, and the only way
   to remove it publicly is to rewrite privately. So publication to a public forge is a derived
   artefact: a filtered history (private folders, expired assets and any purged paths excluded),
   regenerated by a script at each release and force-pushed to the public repository, which is treated
   as disposable. Nobody develops against the public repository.
6. **If a mirror exists anyway, it is the hose, and it is on the author's finger.** A push mirror is
   acceptable only while nothing in the private repository would hurt in public; the day that stops being
   true, the mirror is replaced by the publication script, not patched.

## Gate record (HACCP form)

- Hazard: expired or private material reaching the public repository; a history rewrite forced on the
  private repository.
- Critical control point: the minor-version gate; the publication step of the release.
- Critical limits: expiry sweep returns empty or its removals are in the release commit; the public
  publication is generated from the filter list and contains no path on the private list.
- Monitoring: count of expired assets found per gate; count of private paths in the public publication
  (must be 0); whether the private history was rewritten (must be never).
- Corrective action: add the missed asset type to the manifest rules; add the path to the filter list;
  never rewrite the private history to fix a public leak.
- Verification: the reviewer tier checks the gate record at each release.
- Records: the sweep output and the publication log, attached to the release ticket.
